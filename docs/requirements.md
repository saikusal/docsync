# Requirements — DOCS-101 Docs Sync

> **Status:** Approved
> **Approved by:** saikusal on 2026-10-01
> **Inputs:** user-story/DOCS-101-docs-sync.md, clarifications Q1–Q12 (below)

## 1. User story
> **As a** developer maintaining a GitHub repository,
> **I want** a tool that extracts the facts about my project from its source code and GitHub metadata and keeps the matching README sections up to date,
> **so that** my documentation is always accurate without manual effort, and stale docs are caught in CI before they're merged.

**Personas:** Maintainer (primary, runs the tool), New contributor (reads the README), PR reviewer (needs a drift signal).

## 2. Scope
**In scope (v1):**
- A Node/TypeScript CLI `docsync` with three commands: `init`, `sync` and `check`.
- Two sources: a local directory (`--path`) and a GitHub repository (`--repo owner/repo`).
- Six README sections: `overview`, `tech-stack`, `setup`, `env-vars`, `api-endpoints`, `project-structure`.
- JavaScript/TypeScript source files; **Express** route detection.
- An optional `docsync.config.json`.
- A GitHub Actions workflow in this repo that runs `docsync check` on pull requests.

**Out of scope (v1):**
- Prose generated by an LLM; all content is derived from the source.
- Languages other than JS/TS; frameworks other than Express (Fastify, Next.js, Koa are follow-ups).
- Monorepos / npm workspaces: only the root `package.json` is used (Q6).
- Files other than `README.md` (docs sites, wikis).
- Writing to GitHub: no auto-commit, no auto-PR, no PR comments (follow-up DOCS-102) (Q5, Q9).
- Middleware/auth details per route (Q4).
- Running on a schedule (Q1).

## 3. Functional requirements

### 3.1 CLI and configuration
| ID | Requirement | Priority | Acceptance criteria |
|----|-------------|----------|---------------------|
| FR-1 | The CLI provides `docsync init`, `docsync sync` and `docsync check`, plus `--help` and `--version`. Common options: `--path <dir>` (default `.`), `--repo <owner/repo>`, `--readme <file>` (default `README.md`), `--config <file>`, `--sections <list>`. `--path` and `--repo` are mutually exclusive. | Must | Given `docsync --help`, when run, then all three commands and options are listed. Given both `--path` and `--repo`, when run, then it exits with a usage error and explains why. |
| FR-2 | An optional `docsync.config.json` (in the target root, or given with `--config`) can set: the README path, include/exclude globs, and enabled sections. CLI flags override the file, and the file overrides the defaults. An invalid config is rejected with the field and the reason. (Q12) | Must | Given a config with `"sections": ["env-vars"]`, when `sync` runs, then only the `env-vars` block is updated. Given a config with an unknown key or wrong type, when run, then it exits with a config error naming the field. |
| FR-3 | Input validation: `--repo` must match `owner/repo`; paths must exist and stay inside the target root; section names must be known. | Must | Given `--repo not-a-repo`, when run, then a usage error names the expected format. |

### 3.2 README markers
| ID | Requirement | Priority | Acceptance criteria |
|----|-------------|----------|---------------------|
| FR-4 | Managed blocks are delimited by `<!-- docsync:start <section> -->` and `<!-- docsync:end <section> -->`. Only content between a matched pair is ever changed; everything outside is preserved **byte for byte**, including line endings. | Must | (AC1) Given a README with an `env-vars` block and hand-written text around it, when `sync` runs, then only the block content changes and the text outside is byte-identical. |
| FR-5 | Malformed markers (a start without an end, a nested block, a duplicate section, an unknown section name) are reported with line numbers, and nothing is written. | Must | Given a README with `docsync:start env-vars` and no matching end, when `sync` runs, then it exits non-zero, reports the line number, and the README is unchanged. |
| FR-6 | `docsync init` adds marker blocks for all enabled sections. It appends any missing blocks to an existing README, or creates a minimal README (title + blocks) if none exists. It shows what it will add and requires `--yes` (or interactive confirmation) before writing. It never removes or reorders existing content. (Q2) | Must | Given a repo with no README, when `docsync init --yes` runs, then a README is created containing all six marker blocks. Given a README that already has the `setup` block, when `init` runs, then only the other blocks are added. |
| FR-7 | `sync` and `check` with no README, or with a README that has no markers, exit non-zero with a message that points to `docsync init`. They never create or overwrite files in that case. | Must | (AC6) Given a repo without a README, when `docsync sync` runs, then it exits non-zero, suggests `docsync init`, and no file is created. |

### 3.3 Sections (what is extracted)
| ID | Requirement | Priority | Acceptance criteria |
|----|-------------|----------|---------------------|
| FR-8 | **overview**: project name, description, license, default branch, topics and latest release. Sources, in order of precedence: GitHub API (when available, see FR-17/FR-18), then `package.json`, then the `LICENSE` file. Any field that can't be determined is shown as `Not Found`. The project **name** comes from `package.json`, falling back to the directory or repository name (clarified after the independent review, ICR-9). | Must | (AC4) Given a local repo with no LICENSE file, no `license` field and no GitHub access, when synced, then License shows `Not Found`. |
| FR-9 | **tech-stack**: the runtime (from `engines.node`, else `Not Found`), and production and dev dependencies with their declared version ranges, taken from the root `package.json`. When a lockfile (`package-lock.json`) is present, the resolved versions are shown. | Must | Given `package.json` with `express@^4.19.0`, when synced, then the tech-stack block lists `express` with its version. |
| FR-10 | **setup**: prerequisites (Node version from `engines`, else `Not Found`), the install command (`npm ci` when a lockfile exists, otherwise `npm install`), and every npm script with its exact command line. | Must | (AC4) Given no `engines` field, when synced, then Prerequisites shows `Not Found`. Given scripts `build` and `test`, when synced, then both are listed with their commands. |
| FR-11 | **env-vars**: every environment variable referenced in the source (`process.env.X`, `process.env['X']`, `const { X } = process.env`) or listed in `.env.example`. For each one: the name, the source files where it is used, and **Required** (Yes when at least one use has no fallback such as `\|\|`, `??` or a destructuring default; otherwise No) (Q3). Values are **never** read or shown. A variable found only in `.env.example` is listed with "Required: `Not Found`" and "Used in: `Not Found`" (clarified after the independent review, IDQ-2). | Must | (AC1) Given code that uses `process.env.DATABASE_URL` with no fallback and `process.env.PORT \|\| 3000`, when synced, then `DATABASE_URL` is listed as Required = Yes, `PORT` as Required = No, each with its file. |
| FR-12 | **api-endpoints**: Express routes declared as `app.<method>(path, …)`, `router.<method>(path, …)` or `app.route(path).<method>(…)`, with the prefix applied when a router is mounted via `app.use('/prefix', router)` (when it can be resolved statically). Each route shows: HTTP method, full path, source file (Q4, Q7). Routes whose path is not a static string are listed with the path `Not Found (dynamic)` and their file. | Must | (AC3) Given `router.post('/orders')` mounted with `app.use('/api', router)`, when synced, then the block lists `POST /api/orders` with its source file. |
| FR-13 | **project-structure**: the top-level directories (after exclusions), each with a purpose. The purpose comes from a fixed list of well-known folder names (e.g. `src` = source code, `tests` = tests, `docs` = documentation); anything else shows `Not Found`. | Should | Given folders `src` and `scripts-legacy`, when synced, then `src` shows its purpose and `scripts-legacy` shows `Not Found`. |
| FR-14 | Output is deterministic: rows are sorted (alphabetically, or by path then method for routes) and contain no timestamps, so identical input gives identical output. | Must | (AC2) Given an in-sync README, when `sync` runs twice, then the second run reports "no changes" and the file is byte-identical. |

### 3.4 Commands
| ID | Requirement | Priority | Acceptance criteria |
|----|-------------|----------|---------------------|
| FR-15 | `sync` (local mode) rewrites the stale blocks in place and prints a summary of which sections changed. In `--repo` mode it doesn't write to GitHub; it writes the updated README to `--out <file>`, or to stdout by default (Q9). | Must | Given `--repo owner/repo --out new.md`, when `sync` runs, then `new.md` contains the updated README and no GitHub write call is made. |
| FR-16 | `check` writes nothing. It compares each block with freshly rendered content, prints a per-section drift report showing a unified diff, and exits with code `1` on drift or `0` when everything is in sync. When the `GITHUB_STEP_SUMMARY` environment variable is set, the report is also written as Markdown to the GitHub Actions job summary (Q5). | Must | (AC3) Given code with a new route that isn't in the README, when `check` runs, then it exits with 1, names `api-endpoints`, and shows the missing route. (AC9) Given it runs in GitHub Actions, then the report appears in the job summary. |

### 3.5 Sources
| ID | Requirement | Priority | Acceptance criteria |
|----|-------------|----------|---------------------|
| FR-17 | **Remote mode** (`--repo owner/repo`) reads files and metadata through the GitHub REST API, with optional `--ref <branch|tag|sha>` (default: the default branch). It applies the same scan scope as local mode (Q8). | Must | Given `--repo octocat/Hello-World`, when `check` runs, then the files are read through the API and the same report as for a local clone is produced. |
| FR-18 | **Local mode** reads the file system. GitHub-only metadata (description, topics, latest release) is fetched only when `GITHUB_TOKEN` is set **and** the git `origin` remote points to github.com; otherwise those fields fall back to `package.json`, then `Not Found`. Local mode works fully offline (Q10). | Must | Given no `GITHUB_TOKEN`, when `sync` runs locally, then no network call is made and topics show `Not Found`. |
| FR-19 | Scan scope: JS/TS files (`.js .jsx .ts .tsx .mjs .cjs`). The default exclusions are `node_modules`, `dist`, `build`, `coverage`, `.git`, test files (`*.test.*`, `*.spec.*`, `__tests__/`, `test/`, `tests/`) and anything matched by `.gitignore`. Include/exclude can be overridden in config (Q11). | Must | Given an env var used only in `src/app.test.ts`, when synced, then it is not listed. |

### 3.6 Error handling
| ID | Requirement | Priority | Acceptance criteria |
|----|-------------|----------|---------------------|
| FR-20 | An empty repository (no files, or no commits in remote mode) exits cleanly with the message "repository is empty" and a non-zero code. | Must | (AC7) Given an empty repo, when either command runs, then the message is shown and no stack trace is printed. |
| FR-21 | GitHub API failures produce specific, actionable messages and exit with a non-zero code: invalid or expired token (401), repo not found or no access (404), rate limited (with the reset time in local time), network/timeout, and server errors (5xx, after retries). | Must | (AC8) Given a rate-limited response, when run, then the message says when the limit resets, and the token isn't printed. |
| FR-22 | Unparseable source files are skipped with a warning (file + reason) and don't abort the run. | Should | Given one file with a syntax error, when synced, then the other files are processed and the warning names the file. |
| FR-23 | Stack traces are shown only with `--debug`. | Should | Given an API error without `--debug`, then only the one-line message is shown. |

### 3.7 CI
| ID | Requirement | Priority | Acceptance criteria |
|----|-------------|----------|---------------------|
| FR-24 | This repo has a GitHub Actions workflow that runs on `pull_request`: lint, test, then `docsync check` against this repo's own README (Q1). | Must | (AC9) Given a PR that adds a route without updating the README, when CI runs, then the docs-check job fails with the drift report in the summary. |

### Exit codes
| Code | Meaning |
|------|---------|
| 0 | Success / no drift |
| 1 | Drift detected (`check`) |
| 2 | Usage, configuration or marker error |
| 3 | Source error (empty repo, GitHub API failure, file-system error) |

## 4. Non-functional requirements
| ID | Category | Requirement | Measure |
|----|----------|-------------|---------|
| NFR-1 | Security | The values of environment variables are never read: `.env` files are never opened, and only `.env.example` is parsed, for **names only**. | A test with a `.env` containing a sentinel value: the sentinel appears nowhere in the README, the report, stdout or stderr (AC5). |
| NFR-2 | Security | The GitHub token is read only from the `GITHUB_TOKEN` environment variable and never accepted as a CLI argument. All output passes through a redactor that masks token-shaped strings. | A test with the token set and an API error forced: the token is absent from all output. |
| NFR-3 | Security | Least privilege: only read-only GitHub API calls are made; the tool works with a fine-grained token that has `contents:read` and `metadata:read`. | A code review confirms no write endpoints are used. |
| NFR-4 | Security | Paths read in remote mode and local mode are validated (no path traversal outside the target root). | A test with a crafted `../` path is rejected. |
| NFR-5 | Performance | A local repository of about 500 source files syncs in under 10 seconds on a typical developer laptop. | Benchmark test on a generated 500-file fixture. |
| NFR-6 | Performance | Remote mode limits API usage: one tree request plus content requests only for in-scope files, and it respects rate-limit headers. | Request count asserted in mocked tests. |
| NFR-7 | Portability | Runs on Windows, macOS and Linux with Node.js 22.12 or later (supported LTS lines only). | CI matrix: ubuntu + windows (+ macOS optional) on Node 22 and 24. |
| NFR-8 | Reliability | `sync` writes atomically (temporary file, then rename), so an interrupted run never leaves a half-written README. | Code review + test. |
| NFR-9 | Testability | All GitHub access goes through one interface that can be replaced in tests; the whole test suite runs with no network access. | Tests pass with the network disabled. |
| NFR-10 | Maintainability | Each section is a self-contained extractor + renderer module; adding a section requires one new module and a registry entry, with no changes to the marker, sync or check code. | Code review. |
| NFR-11 | Usability | Every error states what went wrong and what to do next; `--help` documents every command and option. | Review of error messages against FR-20–FR-23. |
| NFR-12 | Dependency safety | Dependencies are version-pinned via the lockfile; `npm audit` reports no high or critical vulnerabilities. | `npm audit --audit-level=high` passes in CI. |

## 5. Assumptions and constraints
- A-1: The story says Node 18+, but Node 18 and Node 20 are both end-of-life (Node 20 since 2026-04-30), so the minimum is **Node 22.12** (current library majors such as commander 15 and vitest 5 require it). *Amended in Phase 2 and confirmed by saikusal.*
- A-2: The exit-code scheme in §3 (0/1/2/3) is a proposal so that CI can tell "docs drifted" apart from "tool failed". *Confirmed by saikusal.*
- A-3: npm scripts are documented by their command line only; the tool doesn't invent descriptions of what a script does (FR-10).
- A-4: Folder purposes come from a fixed list of well-known folder names, and anything else is `Not Found` (FR-13).
- A-5: Only `README.md` at the target root is managed, unless `--readme` or the config says otherwise.
- A-6: GitHub.com only; GitHub Enterprise Server isn't supported in v1.
